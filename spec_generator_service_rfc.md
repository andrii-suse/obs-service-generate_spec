# Architecture Plan: `obs-service-generate_spec` & Zero-Touch Upstream Packaging in Open Build Service

## 1. Executive Summary & Vision

The goal is to provide **zero-touch RPM packaging** directly from upstream Git repositories (GitHub, GitLab, Gitea) within the Open Build Service (OBS). 

Upstream developers without RPM packaging experience will be able to provide only their repository URL. OBS will automatically:
1. Fetch and track Git revisions via `<scmsync>`.
2. Inspect the codebase for common package manifests (`Cargo.toml`, `pyproject.toml`, `go.mod`).
3. Generate valid, idiomatic `.spec` files and vendor dependencies on the fly.
4. Build multi-distribution RPMs in standard network-isolated OBS workers.

If the upstream repository already provides a `.spec` file, the system steps aside with zero overhead or changes.

## 3. Detailed Component Design: `obs-service-generate_spec`

### A. The Signature-Aware No-Op Guard (Version Bump Lifecycle)
The service must strictly maintain idempotency, backwards compatibility, and continuous upgradeability across releases:
1. Inspect the workspace for existing `.spec` files (including service-prefixed files like `_service:*:*.spec`) and inside source archives (`*.tar.*`, `*.obscpio`).
2. **Signature Verification:**
   * If an existing `.spec` file contains `# AUTO-GENERATED by obs-service-generate_spec`, it is recognized as a previous run's artifact. **The generator permits updating and regenerating the spec** with the new version, new dependencies, and updated `.changes` entries.
   * If an existing `.spec` file lacks this signature, it is treated as a custom, human-maintained recipe. **The generator immediately logs a notice and exits cleanly with returncode `0`**, leaving human packaging untouched.

### B. Dynamic Plugin Architecture (`generate_spec.d/`)
The dispatcher executes plugins discovered in standard drop-in directories:
* `/usr/lib/obs/service/generate_spec.d/` (System/package default)
* `/etc/obs/service/generate_spec.d/` (Administrator overrides, higher priority)

#### Priority & Mask Convention
Plugins are named:
`<priority>-<manifest_pattern>`

For example:
```
/usr/lib/obs/service/generate_spec.d/
  ├── 10-Cargo.toml         -> ../plugins/cargo_generator.py
  ├── 20-pyproject.toml     -> ../plugins/pyproject_generator.py
  ├── 25-setup.py           -> ../plugins/setuptools_generator.py
  └── 30-go.mod             -> ../plugins/go_generator.py
```

* **Priorities (00–99):** Deterministic execution. If a repo has both `pyproject.toml` and `Cargo.toml` (e.g. PyO3 Python bindings written in Rust), the lower numeric priority wins.
* **Symlink Masking:** If an administrator symlinks `/etc/obs/service/generate_spec.d/10-Cargo.toml` to `/dev/null`, Cargo auto-generation is disabled.

### C. Integrated Offline Vendoring (Addressing the Multi-Ecosystem Dilemma)
Existing vendor services (like `obs-service-cargo_vendor` or `obs-service-go_modules`) cannot be included in a generic default template because they hard-fail with exit code `1` if their specific manifest is missing (e.g. running `cargo_vendor` on a Python repo aborts the entire OBS pipeline).

To resolve this cleanly:
1. **The Plugin Owns Vendoring:** Because each plugin in `generate_spec.d/` is only invoked when its manifest is detected, the plugin itself is responsible for producing the offline vendor archive (if the ecosystem requires it) before emitting the spec.
2. **Lockstep Guarantees & Cache Validation:** 
   * The plugin runs the vendor command (e.g. `cargo vendor`, `go mod vendor`).
   * The plugin records a SHA256 checksum of the manifest files (`go.mod` + `go.sum`) in `vendor.tar.<compression>.sha256`. On subsequent runs, if the manifest checksum has not changed, the vendor archive is reused without re-downloading dependencies. If dependencies change on a version bump, a fresh vendor archive is automatically created.
   * The plugin writes the `.spec` file with the exact matching `Source1: vendor.tar.xz` and `%prep` unpack directives (`%autosetup -a 1`).
   * Ecosystems that do not require vendoring (such as standard Python using distro packages via `%generate_buildrequires`) skip archive creation entirely.

### D. Standard Plugin Execution Contract
When a manifest matches, the dispatcher delegates execution to the target generator:

```bash
<plugin_executable> \
  --manifest-path <path/to/manifest> \
  --source-dir <workspace_dir> \
  --outdir <OBS_OUTDIR> \
  [--name <override_pkg_name>]
```

**Plugin Expectations:**
* Must parse the project manifest (handling both single packages and multi-project workspaces/monorepos).
* Must create offline vendor archives (`vendor.tar.xz`) in `<OBS_OUTDIR>` if required by the language.
* Must normalize licenses to standard **SPDX expressions** (e.g., `MIT OR Apache-2.0`).
* Must write `<package_name>.spec` directly to `<OBS_OUTDIR>` referencing any generated vendor archives.
* Must return exit code `0` on success, non-zero on unrecoverable error.

### E. 5-Tier Automated Version Resolution
Because manifests like `go.mod` intentionally do not record package versions, the dispatcher implements a 5-tier resolution hierarchy:
1. **Explicit Parameter:** User/template-supplied `--version` (if not `@VERSION@`).
2. **OBS SCM Metadata:** Parses `version:` from `_scmsync.obsinfo` or `*.obsinfo`.
3. **Git Tags & Commits:** Evaluates `git describe --tags --exact-match` (clean semver tags like `0.40.5`) or `git describe --tags --always` (`11.5.4+git20.b6d9a35f`).
4. **Source Archive Filename:** Extracts version regex from existing archives in the workspace (e.g. `croc-10.1.1.tar.gz`).
5. **Fallback Placeholder:** Emits `@VERSION@` for downstream substitution by `obs-service-set_version`.

## 4. Initial Ecosystem Specifications

### 1. Rust (`Cargo.toml`)
* **Detection:** `Cargo.toml` in repository root.
* **Metadata Extracted:** `[package]` name, version, description, license, edition.
* **Offline Strategy:** Relies on `cargo_vendor` running prior to or within the spec.
* **Generated Spec Features:**
  * Uses `%autosetup -a 1` (extracts `vendor.tar.xz`).
  * Injects `.cargo/config.toml` offline replacement directives.
  * Runs `cargo build --release --offline`.
  * Installs compiled binaries from `target/release/` to `%{_bindir}`.

### 2. Python (`pyproject.toml` / PEP 517 & 621)
* **Detection:** `pyproject.toml` in repository root.
* **Metadata Extracted:** `[project]` name, version, summary, license, dependencies.
* **Distro Strategy:** Leverages modern RPM packaging macros (`%pyproject_buildrequires`, `%pyproject_wheel`, `%pyproject_install`).
* **Generated Spec Features:**
  * Includes `%generate_buildrequires` block for dynamic dependency resolution.
  * Standard `%files` macro targeting `%{python3_sitelib}/*`.

### 3. Go (`go.mod`)
* **Detection:** `go.mod` in repository root.
* **Offline Strategy:** Relies on `vendor.tar.<compression>` produced by running `go mod vendor` or packing existing `vendor/`.
* **Generated Spec Features:**
  * Uses `go build -mod=vendor -buildmode=pie`.
  * Detects entrypoint in root (`main.go`), `cmd/<pkg>/main.go`, or `examples/<pkg>/main.go`.
  * Auto-detects systemd service files (`<name>.service`) and injects `%service_add_*` / `%service_del_*` scriptlets.
  * Auto-detects man pages (`<name>.1` or `packaging/<name>.1`) and packages into `%{_mandir}/man1/`.

## 5. OBS Configuration & Template Integration

To achieve "one-click" builds without requiring upstream developers to write XML:

### Option 1: Project-Level Service Template (No core OBS changes)
In the target project (e.g. `home:developer:github-packages`), configure `_project/_service`:
```xml
<services>
  <service name="tar" />
  <service name="recompress"><param name="compression">xz</param></service>
  <service name="generate_spec" />
  <service name="set_version" />
</services>
```
*Any empty package with `<scmsync>` in this project automatically executes this pipeline.*

### Option 2: Core OBS Bridge Extension (`Service.pm`)
In `src/backend/BSSrcServer/Service.pm`, extend `generate_obs_scm_bridge_service` to append `generate_spec` to the in-memory execution plan when no explicit `_service` exists.

## 6. Zero-Token CI Authentication (Phase 2 Roadmap)

To trigger builds from GitHub Actions, Gitea Actions, or GitLab CI without storing permanent tokens:

1. **OIDC Token Issue:** The CI runner requests an OpenID Connect (OIDC) JWT token from the SCM host.
2. **OBS Verification:** OBS receives the token at `/trigger/scmsync`, validates the cryptographic signature against the SCM host's JWKS (`.well-known/openid-configuration`).
3. **Implicit Whitelist via Database:** OBS reads the `repository` and `branch` claims from the JWT and looks up matches in the existing `scmsync` database index:
   ```sql
   SELECT project, package FROM scmsync 
   WHERE scmsync_repo = ? AND scmsync_branch = ?;
   ```
4. **Trigger:** If matched, the build is authorized and run under the package maintainer's account with no secrets ever saved in the git repository.

## 8. Summary of Advantages

* **Non-invasive:** Does not break existing packaging or require changes to upstream Git repositories.
* **Gradual Onboarding:** Upstream can use automated generation initially and switch to a custom `.spec` file at any time without reconfiguration.
* **Modular:** New programming languages and frameworks (Node.js, Zig, D, etc.) can be supported by simply dropping a new plugin script into `generate_spec.d/`.
